# Ergouzi Docs Modern Rebuild Spec

## 1. 结论

本项目适合采用“渐进式重构”方案：

- 先搭建一个基于 `Vite + React + TypeScript` 的新前端骨架。
- 旧站内容先保留，作为迁移参考和回退保障。
- 教程内容逐步从 `assets/content.js` 迁移到 Markdown。
- 图片继续复用现有 `assets/` 目录。

第一阶段不追求一次性把整个文档站全部切到 React。  
真正要先解决的是两件事：

1. 新项目结构要先站稳，后续迁移才不会越迁越乱。
2. 旧内容必须可参考，避免迁移过程中丢失文案、截图顺序和业务说明。

另外，首页需要明确增加一个简短的 `CC Switch 快速配置 Codex` 文字说明模块，用来帮助新用户快速判断是否该走这条路径。

## 2. 先质疑：真实目标和隐含问题

### 2.1 真实目标

表面上是在“重写一个现代化前端网站”，但更真实的目标是：

1. 让第一次接入中转站的用户更容易看懂。
2. 让后续维护教程的人改内容更轻松。
3. 让迁移过程可控，不因为换框架把现有内容体系打断。

### 2.2 当前真正的问题

当前项目的问题不只是“页面不够现代”，而是：

- 内容、路由、展示耦合在 `assets/content.js` 里。
- 文档越多，维护 JS 模板字符串越痛苦。
- 一次性全量改造会把“技术切换风险”和“内容迁移风险”叠加在一起。

### 2.3 关键约束

- 现有站点还能工作，不能把它当废稿直接推倒。
- 现有图片资源已经比较完整，应该尽量复用。
- 项目本质是教程站，不需要先引入后端、数据库、CMS。
- 迁移过程中必须可以对照旧内容，必要时可回退。

## 3. 再精简：第一阶段只做真正需要的事

### 3.1 第一阶段必须有

- React 项目骨架
- 基础路由和页面布局
- Markdown 内容渲染链路
- 旧站内容保留与参考方式
- 首页新版结构
- `CC Switch 快速配置 Codex` 首页简短说明
- 至少一组教程的迁移验证
- 现有图片资源复用
- 移动端可读性

### 3.2 第一阶段先不做

- 全量文档一次性迁移
- 复杂 CMS
- 服务端搜索
- 登录态
- 多语言
- 后台编辑系统
- 激进的自动化迁移脚本

### 3.3 边界定义

第一阶段是“新框架落地 + 迁移路径跑通”，不是“全站一次性完工”。

## 4. 再优化：技术方案与取舍

### 4.1 框架选择

推荐：`Vite + React + TypeScript`

原因：

- 组件化能力足够，适合做导航、正文页、目录、搜索、提示框、图片展示。
- 启动和构建轻，适合这个项目体量。
- 比继续维护原生 JS 更适合长期演进。
- 又没有重到必须承受 Next.js 那一层复杂度。

不优先一次性上更复杂方案的原因：

- 当前最大问题是内容组织，不是 SSR。
- 先把“内容层”和“展示层”拆开，比先追求更重框架更重要。

### 4.2 内容组织方案

目标结构：

```text
content/
  index.md
  guides/
  apps/
  api/
  sdk/
  examples/
```

每篇 Markdown 使用 frontmatter 保存元信息，例如：

```md
---
title: Cherry Studio 配置
group: 应用集成
slug: /apps/cherry-studio
summary: 在 Cherry Studio 中接入 Ergouzi 的完整步骤
keywords:
  - Cherry Studio
  - 教程
order: 10
---
```

职责边界：

- Markdown：存正文内容
- Frontmatter：存导航和页面元信息
- React 组件：负责展示和交互

### 4.3 图片资源策略

保持现有 `assets/` 目录不大动。

规则：

- 迁移阶段继续沿用原图片路径。
- Markdown 直接引用现有图片。
- 优先用已有 `.webp`，没有再用 `.png`。
- 用统一图片组件处理圆角、边框、说明文字和移动端展示。

这样做的好处是：先保留内容稳定性，不把重命名图片这类低价值工作提前。

### 4.4 首页信息架构

首页不该只是文档目录，而应该回答：

1. 我从哪开始？
2. 我该走哪条配置路线？
3. 如果要快速接 Codex，最短路径是什么？

建议首页结构：

1. Hero 区
2. `CC Switch 快速配置 Codex` 简短说明
3. 场景入口卡片
4. 新手推荐路径
5. 常见配置方式
6. 常见问题入口

其中 `CC Switch 快速配置 Codex` 模块要求：

- 是文字版，不依赖用户先点进长教程。
- 足够短，强调“最快路径”。
- 内容应类似：
  - 下载并打开 CC Switch
  - 添加 OpenAI 或 Claude 配置
  - 切到 Codex 所需配置
  - 跳转到完整图文教程
- 配一个明显按钮，进入完整 `CC Switch` 页面。

### 4.5 视觉方向

建议做“现代教程产品风格”，不是花哨营销页。

方向：

- 浅色为主
- 蓝绿系主色
- 暖色只用于提示和重点
- 强调层级、步骤感、卡片感
- 动效轻，阅读优先

这比“为了现代化而堆特效”更适合教程站。

## 5. 再提速：实施路径

### 5.1 总体策略

采用双轨迁移，而不是全量替换。

含义：

- 新 React 项目先建起来。
- 旧站内容暂时保留。
- 新页面逐步替代旧页面。
- 迁移期间可以随时对照旧内容。

这样拆分后，风险会明显降低：

- 框架问题先解决
- 内容问题后解决
- 每次只搬一部分，出错范围更小

### 5.2 分阶段执行

#### 阶段 1：搭新项目骨架

- 初始化 `Vite + React + TypeScript`
- 建立全局布局、基础样式变量、路由
- 搭建首页壳、文档页壳、导航区、目录区
- 保留旧站文件，不删旧实现

#### 阶段 2：跑通 Markdown 链路

- 接入 Markdown 渲染
- 设计 frontmatter 结构
- 实现内容加载和导航生成
- 先用少量页面验证链路

#### 阶段 3：优先迁移首页和高频教程

- 先做新版首页
- 首页补上 `CC Switch 快速配置 Codex` 的文字版说明
- 再迁移最常访问的配置教程
- 每迁一页都对照旧站校验

#### 阶段 4：逐步扩展迁移范围

- 迁移应用接入
- 迁移 API
- 迁移 SDK
- 迁移 Examples

### 5.3 自动化放后面

只有当内容结构稳定后，再考虑：

- 从旧 `content.js` 半自动抽取
- 自动检查图片引用
- 自动生成搜索索引

第一阶段不建议先写复杂迁移脚本，因为那会在结构没定时提前固化错误。

## 6. 架构设计

### 6.1 目录建议

```text
src/
  app/
    router.tsx
    layout.tsx
  components/
    site-header/
    side-nav/
    page-toc/
    search-dialog/
    markdown/
    doc-image/
    code-block/
    callout/
  content/
    loader.ts
    search-index.ts
    toc.ts
  pages/
    home/
    doc/
    legacy/
  styles/
    tokens.css
    globals.css
    prose.css
  types/
    content.ts
content/
assets/
```

模块边界：

- `content/`：存原始 Markdown
- `src/content/`：负责解析内容和索引
- `components/`：通用展示组件
- `pages/`：页面组装层
- `legacy/`：如有需要，提供迁移期旧内容参考入口

### 6.2 路由边界

建议路由由内容元数据驱动，而不是继续维护一份超大页面数组。

新增教程时的理想流程：

1. 新建 Markdown
2. 写 frontmatter
3. 引图片
4. 自动出现在导航和搜索中

### 6.3 Markdown 渲染边界

Markdown 不应直接裸渲染，而应由统一组件接管：

- 标题自动锚点
- 图片替换为统一图片组件
- 代码块替换为统一代码组件
- 引用块替换为统一提示组件

这能保证视觉一致，也方便后续迭代。

是否删除，要等核心页面迁移完成后再判断。

## 8. 验收标准

第一阶段完成后，应满足：

1. 新 React 项目可以正常启动和构建。
2. 旧站内容仍可保留作为参考，不因新项目搭建而丢失。
3. 首页已切到新信息架构。
4. 首页包含 `CC Switch 快速配置 Codex` 的简短文字说明和完整教程入口。
5. 至少一组核心教程完成 Markdown 化，并能正常访问。
6. 现有 `assets/` 图片能在新站中正常展示。
7. 左侧导航、正文区、目录区的阅读结构可用。
8. 页面在桌面端和移动端都可正常阅读。

## 9. 测试策略

### 9.1 功能验证

- React 项目是否可启动
- 路由是否正常
- Markdown 是否渲染正确
- 图片路径是否都可访问
- 首页 `CC Switch` 简短说明是否清楚且可跳转

### 9.2 内容验证

- 新首页是否准确表达关键入口
- 迁移页面是否和旧内容一致
- 截图顺序、步骤说明是否完整

### 9.3 响应式验证

- 桌面端宽屏
- 平板宽度
- 手机宽度

## 10. 风险与应对

### 风险 1：一次性迁移过大

应对：

- 坚持分阶段迁移
- 每次只迁一小批页面

### 风险 2：迁移中内容走样

应对：

- 保留旧站内容作为对照
- 每页迁移后人工核对

### 风险 3：首页做得太重

应对：

- 首页只做“分流和理解”，不做冗长堆叠
- `CC Switch` 模块保持短、明确、可跳转

## 11. 回滚考虑

回滚策略：

1. 迁移期不删除旧站文件。
2. 新站先独立开发和预览。
3. 如果迁移中断，旧站仍可继续作为对外版本。

这意味着回滚成本低，风险可控。

## 12. 当前执行假设

- 你希望长期重构，但不接受一次性激进替换。
- 你希望先搭基础框架，再逐步迁移内容。
- 你希望首页尽快能体现新的用户引导能力。
- 你希望把 `CC Switch 快速配置 Codex` 放到首页做简短入口。

## 13. 批准后执行建议

1. 先初始化 React 项目骨架。
2. 保留旧站代码与内容，作为迁移参考。
3. 先完成首页和 `CC Switch 快速配置 Codex` 简短说明模块。
4. 再迁移一组高频文档，验证 Markdown 链路。
5. 路跑通后，再逐步替换其余文档。
